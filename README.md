# LOCAL-LAB-AI

A portable, **offline**, GPT-style AI assistant built for B.Tech students —
OS/Linux labs, DBMS/Oracle SQL & PL-SQL, coding (C/C++/Java/Python), debugging,
Software Engineering projects (SRS/UML/docs), exam prep, viva prep, and
local document/image (OCR) question answering. Runs entirely on your own
laptop or a USB stick, with no internet connection required for day-to-day use.

```
Windows                          Linux
------------------------------   ------------------------------
Plug in USB. Open PowerShell.    Plug in USB. Open Terminal.
.\start.bat                      ./start.sh
```

That's it. No pip installs, no API keys, no internet, no setup wizard.

---

## 1. What this is

LOCAL-LAB-AI pairs a local LLM (served by [llama.cpp](https://github.com/ggml-org/llama.cpp))
with a small FastAPI backend and a dependency-free web UI, plus a local OCR
pipeline and a local RAG (retrieval-augmented generation) pipeline over your
own documents — all running on-device. Nothing you type, upload, or ask is
ever sent anywhere.

## 2. Features

- **9 assistant modes**: General, OS/Linux Lab, DBMS/Oracle SQL & PL-SQL,
  Software Engineering Project, Coding, Debug, Exam (mark-aware: 1/2/5/10),
  Viva, Document (RAG).
- **Local chat** with streaming responses, Markdown + syntax-highlighted
  code blocks, and one-click copy — all rendered by a small vendored
  renderer, no CDN.
- **Local OCR**: upload a photo/screenshot of a terminal error, Oracle
  error, or handwritten/printed question; text is extracted on-device
  (RapidOCR + ONNX Runtime) and fed to the assistant.
- **Local RAG**: upload PDFs, DOCX, TXT, Markdown, or source code; they're
  parsed, chunked, embedded (a local deterministic hashing embedder — no
  model download required), and retrieved from a local SQLite+NumPy store.
- **Local memory**: conversations, projects/workspaces, and notes persist
  in a local SQLite database. Clear it any time from the UI.
- **Project workspaces**: group conversations and documents per SWE project.
- **Diagnostics & offline verification** built in (`diagnose`, `offline-check`)
  that actually check files and start real processes, not just print "ok".
- **Security by default**: binds to `127.0.0.1` only, no telemetry, no
  analytics, no API key, no automatic code execution.

## 3. Architecture

```
LOCAL-LAB-AI/
├── backend/app/        FastAPI app: api/, core/, modes/, memory/, rag/, ocr/, engine/
├── frontend/static/     Vanilla HTML/CSS/JS UI (no CDN, no build step)
├── engine/              One-time acquisition scripts (llama.cpp binary, model weights)
├── models/llm/          GGUF model file lives here after `prepare`
├── models/ocr/          (unused - RapidOCR bundles its own ONNX models in its pip wheel)
├── runtime/bin/         llama.cpp engine binary lives here after `prepare`
├── runtime/venv/        Isolated Python virtualenv with all dependencies pre-installed
├── config/              default.yaml (committed) + local.yaml (generated by `prepare`)
├── scripts/             Cross-platform launcher implementations (Python, stdlib-first)
├── data/                Local SQLite memory/RAG databases, uploads (git-ignored)
├── tests/               Unit, integration, launcher, and fixture tests
└── start.sh/.bat/.ps1, prepare.sh/.bat/.ps1, diagnose.sh/.bat/.ps1,
    offline-check.sh/.bat/.ps1, deploy-usb.sh/.bat/.ps1
```

The backend auto-starts and manages the llama.cpp `llama-server` process as
a subprocess bound to loopback, and proxies chat requests to its
OpenAI-compatible API. See `docs/ARCHITECTURE.md` for more detail and
`docs/INFERENCE_PROOF.md` for a from-scratch, real (not mocked) proof that
this whole chain works end-to-end.

**Deviation from a literal top-level `app/` folder**: the spec's suggested
tree listed a top-level `app/`; this project places the actual application
package at `backend/app/` (a single FastAPI project) since a separate
top-level `app/` would have been an empty, redundant folder. Everything
else follows the requested structure.

## 4. Requirements

- Windows 10/11 x64 or Linux x64.
- **Python 3.10+ installed once**, to run `prepare` and `start` (see
  "Honest limitations" below for why this project doesn't bundle a fully
  standalone Python interpreter). Nearly every B.Tech lab machine already
  has this.
- ~4 GB RAM minimum (tuned by default for an Intel i3-1005G1 / 3.8 GB RAM
  machine); ~4 GB free disk space for the engine + model + dependencies.
- Internet access for the **one-time** `prepare` step only.

## 5. One-time preparation

```bash
# Linux/macOS
./prepare.sh

# Windows (PowerShell)
.\prepare.bat
```

This creates an isolated virtualenv, installs all Python dependencies,
downloads the real llama.cpp CPU inference engine binary for your platform,
downloads the default local model (Qwen2.5-1.5B-Instruct, Q4_K_M GGUF —
see "Model information" below), verifies OCR is working, hardware-tunes
`config/local.yaml`, and writes `manifest.json`. **Requires internet.**
Run it again any time to repair or update assets — already-installed
components are detected and skipped.

## 6. Windows startup

```powershell
.\start.bat
```

## 7. Linux startup

```bash
./start.sh
```

Both resolve their own directory at runtime (`LOCAL_LAB_AI_ROOT`), so they
work identically from `C:\`, `D:\`, a USB drive, or any Linux mount point —
never hardcoded.

## 8. USB deployment

```bash
./deploy-usb.sh     # Linux
.\deploy-usb.bat    # Windows
```

Detects removable drives, shows you exactly what will be copied and where,
and requires you to type `yes` before copying a single byte. It **never**
formats a drive, **never** deletes existing files, and only ever writes
inside a `LOCAL-LAB-AI/` subfolder on the target. After copying, it
verifies the model/engine checksums and launcher presence on the target.

## 9. Offline operation

Run `./offline-check.sh` / `.\offline-check.bat` any time. It performs real
checks — not just printing `true` — including: GGUF magic-byte validation,
actually running the engine binary with `--version`, actually starting the
backend and hitting `/api/health`, grepping the frontend for zero external
URLs, and confirming no API key is required anywhere in the backend. See
`docs/TROUBLESHOOTING.md` if any check fails.

## 10. Model information

- **Default model**: `Qwen2.5-1.5B-Instruct`, quantized `Q4_K_M` (~1 GB GGUF).
- **Why not "Qwen3.5-2B"?** The original spec named "Qwen3.5-2B Q4_K_M" —
  no such model has ever been publicly released (Qwen's line goes ...,
  Qwen2, Qwen2.5, Qwen3, at sizes 0.5B/1.5B/3B/7B/...; there is no "3.5"
  line and no exact "2B" size). Qwen2.5-1.5B-Instruct is the closest real,
  actively-maintained, appropriately-sized model for the target hardware.
  See `engine/acquire_model.py` for the exact source and how to point at a
  different/larger GGUF via `config/local.yaml` on stronger hardware.
- **Inference engine**: [llama.cpp](https://github.com/ggml-org/llama.cpp),
  official prebuilt CPU release binaries, fetched by `engine/acquire_engine.py`
  directly from GitHub release URLs (resilient to release-asset-naming
  changes; see that file's docstring).
- Conservative defaults (2 threads, 2048-token context, Q8_0 KV cache) target
  an Intel i3-1005G1 with ~3.8 GB RAM; `prepare` tunes these to your actual
  detected hardware.

## 11. Troubleshooting

See `docs/TROUBLESHOOTING.md`. Quick pointers:
- "No Python interpreter found" → install Python 3.10+ and re-run.
- "Engine not running" in the UI → run `./offline-check.sh` to see which
  asset is missing, then re-run `prepare`.
- Model download failed during `prepare` → your network may block
  huggingface.co; see the manual download link `prepare` prints.

## 12. Security

- Backend binds to `127.0.0.1` only by default (`config/default.yaml:
  server.allow_remote`) — changing this is an explicit, documented opt-in.
- Zero telemetry, zero analytics, zero hidden network calls at runtime.
- No API key of any kind is required or accepted.
- Generated code is **never executed automatically** (`security.allow_code_execution: false`).
- See `SECURITY.md` for the vulnerability reporting process.

## Honest limitations (read this)

This project was built autonomously inside a cloud sandbox whose outbound
network policy blocks `huggingface.co` and `modelscope.cn` (confirmed via
repeated 403s), while allowing `pypi.org`, `npmjs.org`, and — importantly —
direct `github.com/.../releases/download/...` URLs. That shaped what could
be *genuinely tested* here versus what is *implemented correctly but
unverified in this environment*:

| Component | Status |
|---|---|
| Backend API, modes, memory, RAG parsing/chunking/embedding/retrieval | **Real, tested** (pytest, this sandbox) |
| Local OCR (RapidOCR) | **Real, tested** — actual ONNX inference on a rendered test image |
| llama.cpp engine binary acquisition + execution | **Real, tested** — actual official release binary downloaded and run in this sandbox and in CI |
| End-to-end inference plumbing (GGUF load, forward pass, HTTP server, streaming) | **Real, tested** with a tiny from-scratch (untrained/random-weight) GGUF — see `docs/INFERENCE_PROOF.md`. Output is gibberish by design; this proves the *pipeline*, not answer quality. |
| Real pretrained Qwen model download + real answer quality | **Implemented, NOT executable in this sandbox** (huggingface.co blocked here). Will work on a normal machine/network — `engine/acquire_model.py` uses the real, stable HF URL. |
| Windows `.bat`/`.ps1` launchers | **Implemented, code-reviewed, NOT executed** — this sandbox is Linux-only. `.sh` launchers were fully executed here. |
| USB deployment (`deploy-usb`) | **Implemented, NOT executed against a real USB drive** in this sandbox (no removable media attached). Drive-detection logic (`lsblk`/`wmic`) was code-reviewed, not hardware-tested. |
| "Zero host Python" | **Not achieved.** `python-build-standalone`'s release assets are gated the same way as other GitHub release-only content in this specific sandbox for that repository; portable-Python bundling was abandoned in favor of an honest, simpler requirement: Python 3.10+ must already be on the machine (true of virtually every lab PC), and `prepare` creates an isolated virtualenv so no further pip/internet access is needed afterward. |

None of this is hidden in code comments only — it's stated here, in
`docs/INFERENCE_PROOF.md`, and in each acquisition script's own docstring.

## Final status

**Requires one-time preparation** (`prepare`) before first use — this is by
design, matching the spec's own two-mode (`prepare` then `start`) model. It
is **not** a fully self-contained zero-step package: `prepare` needs
internet access to fetch the model weights and the platform-specific engine
binary, and Python 3.10+ must already be installed on the machine.
